## 1. 背景与机会

### 1.1 市场现状

TRPG（桌上角色扮演游戏，俗称"跑团"）在国内持续增长：B 站跑团实录视频动辄百万播放；主流规则体系 DND 5e、COC（克苏鲁的呼唤）在大学社团、桌游店、线上语音社群中活跃度高；相关规则书中文版由官方与民间组持续翻译更新。

但**工具层是国内空白**：

| 竞品 | 现状 | 缺陷 |
|---|---|---|
| Roll20 | 国际主流，虚拟桌面 | 无中文本地化、服务器在境外延迟高、UI 上手门槛极高、免费档限制多 |
| Foundry VTT | 买断制，社区口碑好 | 需 GM 自建服务器（要懂端口映射）、纯英文、无移动端 |
| 国内小程序掷骰器 | 微信群内使用 | 只有掷骰功能，角色卡/战斗管理/规则查阅完全缺失 |
| Excel/纸笔角色卡 | 最普遍的现状 | 手动维护、各算各的、数值易错、无法审计掷骰 |

### 1.2 核心机会

跑团玩家的工具链是**碎片化且互不信任**的：角色卡在 Excel、掷骰在微信群小程序、规则翻 PDF、战斗顺序 GM 纸上画表。最痛的三个点：

1. **数值不一致**：同一规则，GM 的表和玩家的卡算出的结果不同——因为都是各自手动维护。
2. **掷骰不可信**：线上跑团"你真掷出 20 了吗"全靠人品，无审计、无公信力。
3. **GM 负担过重**：主持人要同时当故事讲述者、规则裁判、记账员、掷骰公证人。GM 是跑团的稀缺资源，GM 劝退 = 团散伙 = 用户流失。

**这三个痛点对应同一个解法：一个"规则即契约"的多端平台**——角色卡、检定公式、掷骰结果由同一套领域模型驱动，所有端自动一致，掷骰服务端公证。

### 1.3 与现有技术资产的协同

本产品将采用**契约驱动开发**（fe-be-contract-harness）：

- 角色卡 schema、检定公式、状态效果全部以 OpenAPI 契约定义为 SSOT；
- GM 台（vue）、玩家 H5（react）、规则引擎（node）、存档结算（java）由契约四栈生成；
- **harness 的跨栈一致性校验直接成为产品能力**：玩家端显示的护甲值与 GM 台掷骰引擎取的加值，源自同一契约并经一致性门控——"我卡上 16 你算 14"这类事故在架构上不可能发生；
- 产物 hash 校验与 fail-closed 门控对应产品承诺：**战役数据绝不能错、掷骰记录不可篡改、可回放审计**。

## 2. 产品定位与价值主张

**一句话定位**：让 GM 只需要专心讲故事、让掷骰可信可审计的线上跑团工坊。

**目标用户分层**：

| 用户 | 一句话画像 |
|---|---|
| GM（主要付费者） | 25~35 岁，带过 3 场以上团，被记账/算数/仲裁折磨过 |
| 玩家 | 18~30 岁，每周或每两周跟一次团，目前用 Excel 管角色卡 |
| 团队/社团 | 大学社团、桌游店常驻团，5~8 人固定队伍 |

**核心价值主张**（按优先级）：

1. **V1 一致**：所有端、所有人看到的数值来自同一契约，永不打架。
2. **V2 可信**：掷骰在服务端公证，结果不可篡改、可回放——"这个平台的骰子不会说谎"。
3. **V3 卸负**：GM 不再记账、不再画表、不再口算加值——只讲故故事。

**差异化壁垒**：规则引擎 + 可审计掷骰流水 + 多端一致性，三者组合目前国内无同类产品；且规则包生态（UGC）形成网络效应后迁移成本高。

## 3. 用户旅程（关键场景）

### 3.1 场景 A：线上团（主流，占比预计 70%）

周五晚 8 点，GM 小林和 4 名玩家各自在家，语音用 Discord/飞书。

1. GM 提前 30 分钟打开工作台：加载上周存档，NPC 阵容、剧情线索原样恢复。
2. 玩家手机扫码/输团号入团，手机上看到自己角色卡最新状态（上周战斗残留的"中毒"还在）。
3. 开团：GM 描述酒馆场景，投屏共享地图 token。玩家阿伟说"我上前搭话"——手机上点【魅力检定】，系统掷 D20 出 17+3=20，大屏弹出金色特效"大成功"，GM 接着演酒保。
4. 战斗爆发：GM 一键【先攻】，全团掷骰自动排序入队，大屏显示行动队列，轮到谁高亮谁——再也不会漏人。
5. 玩家密谋：阿伟私聊 GM"我把匕藏进袖子"，其他玩家不可见。
6. 散团：战报自动生成——今晚谁输出最高、剧情大事记、阿伟的运气曲线，一键发群里。

### 3.2 场景 B：线下团（桌游店/社团，占比预计 30%）

桌游店包间，实体骰子 + 大屏电视投 GM 工作台看板。地图 token 在大屏拖动，所有人围观；玩家仍用手机端管自己的卡和私聊。**线上线下混合**：实体骰的玩家可手动录入结果，录入后进入同一审计流水（标注"手动录入"）。

### 3.3 场景 C：GM 备团（独立且高频的子场景）

周二晚，GM 小林备团：在战役面板里建下周的 NPC（挂秘密标签）、预置 3 张地图、写剧情线索卡。备团进度云端保存，周五开团时一键恢复。**备团体验是 GM 留存的关键**，独立于开团场景单独优化。

## 4. 功能需求

### 4.1 优先级定义

- **P0（MVP）**：上线必须，砍掉则产品不成立。目标 3 个月内可跑通第一场真实团。
- **P1（第二迭代）**：显著提升留存/传播，上线后 1~2 个月内补齐。
- **P2（远期）**：商业化与生态。

### 4.2 P0 —— 首个可用版本（"能跑完一场 DND 团"）

#### F1 账号与团队（P0）

- F1.1 手机号/微信登录，昵称 + 头像。
- F1.2 GM 建团：团名、规则体系（MVP 仅 DND 5e）、开团时间、团号/二维码。
- F1.3 玩家凭团号入团；GM 可踢人。团内角色绑定玩家。
- F1.4 一个玩家一个团内 1~N 个角色卡（多角色备卡）。

#### F2 角色卡系统（P0，产品地基）

- F2.1 基于 DND 5e SRD 规则生成角色卡模板：六大属性、衍生值（AC/HP/先攻/熟练加值）、豁免、技能表、装备栏、法术位。
- F2.2 属性/装备/状态变更时**衍生值服务端自动重算**，全端同步——"体质 +2 后 HP 上限自动变"。
- F2.3 状态效果（buff/debuff）：带持续时间与结算规则（如"祝福：攻击检定与豁免 +1d4，持续 3 轮"），轮次推进时自动结算与提醒。
- F2.4 角色卡历史快照：每次战斗开始前自动存档，支持回滚误操作。

#### F3 掷骰与检定引擎（P0，信任根基）

- F3.1 服务端公证掷骰：所有掷骰请求由规则引擎执行，结果落**不可篡改流水**（序号、时间、公式、原始值、加值、目标、成败）。
- F3.2 公式掷骰：支持表达式 `2d6+3`、`1d20+5 vs DC15`、优势/劣势（双骰取高/低）。
- F3.3 检定三件套：属性检定、豁免检定、攻击骰——GM 下发或玩家自点，走同一引擎。
- F3.4 大成功/大失败判定（自然 20/自然 1），触发全端特效与音效。
- F3.5 **手动录入通道**：线下团实体骰场景，玩家/GM 可录入"实际掷出 13"，录入记录标注来源，同样进流水。
- F3.6 掷骰流水查询：任意时刻可拉取本团完整掷骰历史（审计页）。

#### F4 战斗管理（P0）

- F4.1 先攻队列：GM 一键发起全团先攻掷骰（含敌方 NPC），自动排序，支持手动插队（如"迟缓"状态）。
- F4.2 回合推进：轮到谁大屏/玩家端高亮；"下一轮"时状态效果自动结算倒计时。
- F4.3 敌方 NPC 卡：GM 快速建/从怪物模板库拖入，HP 条 GM 可见、玩家不可见具体数值。
- F4.4 死亡豁免：HP 归零自动进入死亡豁免流程（DND 5e 三败/三胜机制）。

#### F5 GM 工作台（P0）

- F5.1 战役面板：当前场景描述、NPC 列表（可挂 GM-only 秘密/剧情线索）、私有笔记。
- F5.2 快速操作盘：常用检定/伤害/治疗/加状态的一键按钮（快捷施法条）。
- F5.3 规则速查：内置 DND 5e SRD 中文规则条目，按关键词检索，GM 可一键把某条规则卡片推送到玩家端。
- F5.4 备团模式：脱机编辑战役（NPC/地图/线索卡），云端保存，开团恢复。

#### F6 玩家端 H5（P0）

- F6.1 电子角色卡（只读视图 + 可编辑自己卡，编辑全端同步）。
- F6.2 常用掷骰按钮（自配置快捷栏）。
- F6.3 战斗队列实时视图 + 轮到自己时震动/弹窗提醒。
- F6.4 私聊 GM 通道（团内密谋，其他玩家不可见）。
- F6.5 个人冒险日志：按团次自动记录本角色经历的事件。

#### F7 大屏看板（P0 简版）

- F7.1 团队投屏页：战斗队列 + 掷骰结果特效 + 场景标题。MVP 不做地图（见 P1），以"事件流大屏"降低首版复杂度。

#### F8 战报（P0）

- F8.1 散团自动生成战报：本场大事记、伤害/治疗/击杀榜、每位玩家掷骰运气统计（平均点数、大成功次数）。
- F8.2 战报分享卡片（长图/H5 链接），分享到微信群的社交货币。

### 4.3 P1 —— 留存与传播（上线后 1~2 个月）

- **F9 地图与 token（P1 首位）**：网格地图上传、token 拖动、距离计算、范围模板（火球术 20 尺）；多端实时同步。
- **F10 COC 规则包**：第二规则体系（理智值/幸运检定/技能成长标记），验证规则包架构的可扩展性。
- **F11 音频集成**：内置语音房（或深度对接现有语音平台），掷骰音效/战斗音乐由场景触发。
- **F12 GM 工具深化**：随机生成器（名字/酒馆/遭遇/宝物）、 Initiative 音乐盒（战斗音乐包）。
- **F13 团队日历与开团提醒**：开团时间提醒（微信服务号/订阅消息）。

### 4.4 P2 —— 商业化与生态

- **F14 订阅分层**（详见 §7）。
- **F15 规则包/战役素材市场**：GM 上架自制战役、自制规则包、地图素材，平台抽成——UGC 生态飞轮。
- **F16 桌游店模式**：大屏端独立 App 化、多团并发看板、店内会员系统打通（B 端订阅）。
- **F17 观战/直播模式**：看板只读链接分享，允许观众围观战斗（内容传播入口）。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 一致性 | 角色数值全端一致由架构保证（契约 SSOT + 一致性门控），**不允许端上自行计算衍生值** |
| 掷骰可信 | 掷骰流水只追加不可改写；披露随机数生成方案（服务端 CSPRNG），接受第三方复核 |
| 实时性 | 战斗队列/token/角色卡变更端间同步延迟 ≤ 1s；语音可走外部平台（P0） |
| 离线容错 | 玩家端断网重连后自动补同步；GM 断线 3 分钟内可重连恢复现场 |
| 数据安全 | 团内 GM-only 数据（NPC 秘密/剧情线索）在 API 层隔离，玩家端任何接口不可拉取；战役存档每日快照，误删 30 天可恢复 |
| 性能 | 单团并发 ≤ 12 端（5 玩家+GM+投屏），回合操作 P95 < 500ms |
| 合规 | 掷骰不涉及真实货币/虚拟财产兑换（合规边界：纯游戏工具）；用户内容（战役/规则包）审核机制 P2 前上线 |

## 6. 明确不做（Non-goals）

1. **不做真实货币对赌**：任何形式的掷骰结果换钱、虚拟筹码交易——红线，永不排期。
2. **不做 AI 主持人**：AI GM 与产品定位（GM 是灵魂）冲突，且质量不可控；AI 仅限于 F12 的生成器类辅助工具。
3. **MVP 不做 3D/虚拟形象**：视觉投入产出比低，token 平面表达足够。
4. **MVP 不做语音自研**：接入成熟方案或让用户外挂语音（P1 再评估）。
5. **不支持自定义规则语言**（P2 用规则包配置化替代图灵完备的规则自定义）。

## 7. 商业化设计

### 7.1 定价模型（GM 订阅 + 玩家免费）

| 档位 | 价格（参考） | 权益 |
|---|---|---|
| 免费 | ¥0 | 1 个活跃团、DND 5e 官方模板、基础掷骰流水、7 天战报 |
| 团长 Lite | ¥19/月 | 3 个活跃团、无限战役存档、完整流水导出、开团提醒 |
| 团长 Pro | ¥39/月 | 10 个团、备团高级功能、自定义快捷栏/角色卡布局、战报定制水印 |
| 工作室 | ¥199/月 | 桌游店模式（多团看板、店内会员）、多 GM 协作、优先客服 |

设计原则：**玩家永远免费**——玩家规模是 GM 付费的前提，绝不用玩家墙逼 GM 付费（对比 Roll20 的玩家也分层造成的组团摩擦）。

### 7.2 收入飞轮

订阅（现金流）→ 素材市场抽成（GM 赚钱 → 更多 GM 入驻 → 更多付费场景）→ 工作室 B 端（客单价天花板）。

## 8. 成功指标

### 8.1 MVP 验证期（上线后 6 周）

| 指标 | 目标 | 判定意义 |
|---|---|---|
| 完整跑完一场团的比例 | 入团用户 ≥ 40% 走完一场 ≥ 2h 的团 | 产品核心循环成立 |
| GM 建团 → 开团转化 | ≥ 50% | 备团体验不劝退 |
| 战报分享率 | ≥ 25% 的团分享过战报 | 自传播机制成立 |
| 7 日团内留存 | 玩家 ≥ 60% 返回 | 验证"跟团"黏性 |

### 8.2 增长期（3 个月）

付费 GM 转化 ≥ 5%；自然新增 GM 中老带新（邀请）占比 ≥ 30%；素材市场上架 ≥ 100 个付费素材。

## 9. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| SRD 中文化与版权：DND 5e SRD 是 OGL 开源，但中文翻译文本版权模糊 | 高 | MVP 只用 SRD 开源条款自译关键规则；不复制官方中文规则书文本；COC（也是 OGL）做第二体系时同此标准 |
| 语音平台依赖 | 中 | P0 明确定位"配合你现有语音使用"，不做深度绑定 |
| GM 习惯迁移成本（Excel/纸笔惯性） | 中 | 角色卡支持 CSV 一键导入；首团引导（checklist 式开团向导） |
| 小众市场天花板 | 中 | 以 GM 订阅 ARPU 而非 DAU 考核；工作室 B 端打开桌游店第二曲线 |
| 实时多端同步复杂度 | 技术 | 契约驱动 + 事件溯源（harness events 机制复用），同步以事件为原子单位而非字段 diff |

## 10. 开放问题（待澄清）

1. 语音方案：P0 是否接声网/腾讯云 WebRTC 快速版，还是完全外挂？（影响 P1 F11 排期）
2. 微信登录 vs 手机号登录优先级（小程序分发 vs H5 分发路线之争，影响获客渠道）。
3. 手动录入掷骰是否限制 GM 权限可关（部分 GM 想强制全公证）——建议做成团长开关，待用户访谈确认。
4. 素材市场抽成比例（15% vs 30%，参考 App Store/Steam 定价生态）。
5. 大屏端 MVP 事件流 vs 完整战斗看板的裁剪边界，待设计稿评审确认。

## 12. 附录：与 harness 开发流程的对接约定

- 本 PRD 评审通过后进入 harness `spec` 流水线：PRD → 技术方案（接口分析/代码库分析）→ 编码。
- 四域契约初稿划分（供 spec 阶段展开）：
  1. **团队/会话域**：团、成员、权限、邀请
  2. **角色域**：角色卡 schema、属性/衍生值/状态效果、快照回滚
  3. **规则与掷骰域**：检定公式、掷骰流水（append-only）、手动录入
